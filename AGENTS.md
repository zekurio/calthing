# Repository Guidelines

## Project Structure & Module Organization

The Deno service starts in `src/main.ts`. Keep application logic in modules under `src/`:
`upstream/` calls Radarr/Sonarr, `services/fetcher.ts` manages upstream retrieval and caching,
`services/ical.ts` renders feeds, `config.ts` parses YAML, and `http/` owns the Elysia handlers and
static file serving. Shared event types live in `src/domain/event.ts`; API types shared with the
frontend live in `shared/api.ts`.

The Svelte frontend is in `frontend/src/`; reusable UI belongs in `frontend/src/components/`, while
API, date, and query helpers belong in `frontend/src/lib/`. Backend tests live in `tests/` with
static fixtures in `tests/fixtures/`. Use `config.example.yaml` as the configuration template. Nix
packaging, the NixOS module, and the dependency-hash script are in `nix/`.

## Build, Test, and Development Commands

- `devenv up` starts the Deno API on `:8080` and Vite on `:5173`; Vite proxies API and calendar
  requests to the backend.
- `deno task test` runs the backend test suite.
- `deno task check` type-checks `src/`, `shared/`, and `tests/`, then runs svelte-check on the
  frontend.
- `deno task frontend:build` creates the production frontend bundle.
- `deno task start -config config.yaml` runs a production-style local server.
- `nix build` verifies the reproducible package build.

Dependencies are managed through `deno.json` and `deno.lock`; `vendor/` (jsr) and `node_modules/`
(npm) are generated by `deno install` and never committed. After changing dependency versions, run
`deno install`, commit the updated `deno.json` and `deno.lock`, and refresh `denoDepsHashes` in
`nix/package.nix` with `nix/update-deps-hashes.sh`.

Update the iCal golden fixture `tests/fixtures/expected.ics` only for intentional rendering changes;
the test compares output byte-for-byte.

## Coding Style & Naming Conventions

Format with `deno fmt` (single quotes, no semicolons, 100-column width) and lint with `deno lint`;
both exclude `frontend/` and `vendor/`, and fmt also skips `tests/fixtures/`. TypeScript is strict
with `noUncheckedIndexedAccess` and `verbatimModuleSyntax`. Keep errors contextual, for example
``throw new Error(`parse config: ${path} must be a string`)``. Name Svelte components in
`PascalCase` (for example, `EventChip.svelte`) and modules and helpers in lower camel case.

## Testing Guidelines

Add `*.test.ts` files under `tests/` beside the existing suites. Name tests as behavior sentences
(`Deno.test('ARR errors name the instance and bound
upstream body text', ...)`) and use `t.step`
where several inputs share an expectation. Exercise endpoint status, response content, and invalid
input; use static fixtures in `tests/fixtures/` rather than live ARR services. Run both
`deno task test` and `deno task check` for changes that affect the web experience.

## Commit & Pull Request Guidelines

Follow the existing Conventional Commits style (`feat: add arr-cal-proxy
service`,
`refactor: migrate service and tooling to Deno`) with concise, imperative subjects. Keep commits
scoped. Pull requests should explain the user-visible effect, describe configuration or API changes,
link relevant issues, and include UI screenshots when frontend behavior changes.

## Security & Configuration

Never commit `config.yaml`, API keys, or tokens. Use `${VAR}` references in configuration and
document settings in `config.example.yaml` and the README. Treat instance names as stable because
they form calendar event UIDs.
